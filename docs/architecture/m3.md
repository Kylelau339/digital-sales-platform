# M3 architecture

M3 adds four operational capabilities without changing the M1/M2 ownership or delivery model.

## Email

`apps/api/src/email/provider.ts` provides an `EmailProvider` abstraction:

- `smtp` uses `nodemailer` with pooled connections and explicit connection, greeting, and socket timeouts.
- `console` is development-only and prints the message to stdout.
- Production configuration requires `EMAIL_PROVIDER=smtp` and SMTP credentials.

`createEmailVerification` still stores only an HMAC of the six-digit code. After each send it appends a row to `email_delivery_logs` with recipient, provider, status, provider message id, and error code. Message bodies and codes are never stored in the log.

## Refund flow

1. A buyer creates a complaint. Rights-related reasons are accepted at any time; refund-eligible reasons use the order's frozen policy window.
2. An admin loads the complaint detail. `evaluateRefundPolicy` evaluates the frozen snapshot, download count, payment status, and currency.
3. Approval reserves one active `refund_requests` row, then calls Stripe Refund outside the SQLite transaction with idempotency key `refund:<complaintId>`.
4. A second transaction records the Stripe refund id, inserts the refund ledger row, and, on success, finalizes:
   - order `payment_status='refunded'`, `order_status='refunded'`
   - complaint `refund_decision='approved'`, `status='resolved'`
   - all entitlements for the order `status='revoked'`
   - complaint timeline and append-only audit rows
5. `refund.created`, `refund.updated`, and `refund.failed` reconcile asynchronous or out-of-band status. `payment_event_inbox` deduplicates events, and `refund_requests.stripe_refund_id` is unique.

External Stripe calls never run inside a SQLite transaction. The trade-off is a small window between Stripe success and database finalization; the refund webhook is the reconciliation path.

## Financial invariants

- All amounts are non-negative integer minor units.
- `orders.platform_fee_bps` is a rate snapshot. `platform_fee_cents + seller_amount_cents = price_cents`.
- A full refund reverses:
  - `product_refund_cents = price_cents`
  - `tax_refund_cents = amount_minor - price_cents`
  - `platform_fee_reversal_cents = platform_fee_cents`
  - `seller_reversal_cents = seller_amount_cents`
- `refund_requests` enforces `product_refund_cents = platform_fee_reversal_cents + seller_reversal_cents`.
- One active refund request per complaint; one Stripe refund id per request.
- Seller earnings report gross sales, platform fees, seller refund reversals, net earnings, and tax separately.

## Takedown

`POST /admin/templates/:id/takedown` runs in one SQLite transaction:

- `suspend`: approved → suspended; the existing catalog, checkout, and download guards hide and block the listing.
- `remove`: any non-removed state → removed; clears `current_version_id` and `review_target_version_id`, revokes entitlements, and records `template_takedowns`.
- The audit diff records the previous status, mode, current version, and revoked entitlement count, plus request id, IP, and user agent.

## Seller earnings

`createEarningsService` aggregates orders and succeeded refunds in JavaScript using integer arithmetic. Sales are bucketed by `orders.paid_at`; refunds are bucketed by `refund_requests.created_at`. This keeps a refund in the period it occurred rather than rewriting historical sales. Tax is reported separately and never included in seller net earnings.

## Frontend

- `/seller/earnings` renders the seller dashboard.
- `/admin` records tab loads real complaints, approved templates, and audit rows.
- `/complaints` binds buyer form state and submits idempotently.
- Refund and takedown dialogs are generated by the presentation adapter; API calls and dialog state remain in `main.tsx`.
- `render-functions.js` remains a pure HTML-string renderer with no network calls or listeners.
